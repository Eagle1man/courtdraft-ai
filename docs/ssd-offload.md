# Выгрузка части модели на SSD: применимо ли для vikhr-7b

Проверено на этой машине 2026-10-31: Windows 11, 7,8 ГБ ОЗУ (свободно
1–2 ГБ), видеокарты нет, Ollama 0.40.13. Модель `vikhr-7b:latest` —
GGUF-блоб 3,95 ГБ.

## 1. Что делает Ollama

В логе сервера (`%LOCALAPPDATA%\Ollama\server.log`) на каждой загрузке:

```
level=INFO source=sched.go:1183 msg="disabling mmap for llama-server load
by default" model=... reason=cpu
level=INFO source=sched.go:658 msg="system memory" total="7.8 GiB"
free="1.1 GiB" free_swap="10.2 GiB"
```

То есть **Ollama 0.40.13 отключает mmap для CPU-загрузки**. Веса читаются
в обычную память процесса, а когда её не хватает — уходят в файл
подкачки Windows (`free_swap` 10–11 ГБ). Это не «частичная выгрузка на
SSD» в смысле mmap: грязные страницы нужно записывать, отсюда и
медленность, и износ диска. Флага включить mmap в `ollama serve` нет
(`--help` его не содержит), поэтому через Ollama метод недоступен.

## 2. Что делает llama.cpp (тот, что уже есть в Ollama)

Ollama ставит с собой `llama-server.exe`:

```
C:\Users\diorl\AppData\Local\Programs\Ollama\lib\ollama\llama-server.exe
```

В llama.cpp mmap — режим **по умолчанию**; отключается флагом
`--no-mmap`. Положительного `--mmap` в этой сборке нет: он отвечает
`invalid argument`. Блоб Ollama — обычный GGUF, его можно скормить
напрямую:

```powershell
$bin = "C:\Users\diorl\AppData\Local\Programs\Ollama\lib\ollama\llama-server.exe"
$blob = "D:\ollama\models\models\blobs\sha256-a37244f1d3451becd4350041635dcabe7742ad1d2f875616b0d823750efe43ce"
& $bin -m $blob -ngl 0 -c 1024 -t 4 --host 127.0.0.1 --port 11435
```

Замер на этой машине:

| Этап | Факт |
|---|---|
| Загрузка модели | ~74 с (ленивое чтение с SSD) |
| Память сразу после загрузки | 0,5–1,6 ГБ на процесс вместо 3,95 ГБ файла |
| Первый запрос (32 токена) | 234 с, холодные страницы |
| Второй запрос (16 токенов) | 36,8 с |
| Память после прогона | поднимается до размера модели (3,9 ГБ) — страницы прочитаны |

## 3. Вывод

**Метод применим, но не через Ollama.** Варианты по убыванию пользы:

1. **llama.cpp напрямую** (`llama-server.exe` + GGUF-блоб Ollama) —
   mmap работает: файл модели остаётся на SSD, в памяти только
   прочитанные страницы, ОС может их выбросить без записи. Это и есть
   «частичная выгрузка на SSD» без износа от подкачки.
2. **Ollama как сейчас** — работает, но через файл подкачки: медленно и
   с записью на SSD. Для разовых прогонов приемлемо.
3. **Меньшая модель** (`qvikhr` 1,7B, `qwen2.5:1.5b`) — быстрее обоих
   вариантов, но качество ниже.

Ограничения варианта 1:

- интерфейс llama.cpp — `/v1/chat/completions` и `/completion`, а не
  `/api/chat` Ollama. Приложению нужен адаптер или прокси;
- первый запрос после старта платит за чтение с SSD (у нас 234 с);
- скорость всё равно CPU: 7B не станет быстрым, он станет возможным;
- при нехватке памяти ОС будет вытеснять страницы, и генерация будет
  «дёргаться» — время по разделам непредсказуемо.

## 4. Что это значит для сегодняшней проверки фильтра

Для оценки фильтра на 54 фрагментах 7B не нужен: 54 запроса по 30–240 с
— это часы. Набор лучше прогнать на `qvikhr:latest` (1,3 ГБ, влезает без
подкачки) и, для сравнения, на `qwen2.5:1.5b`.

Выгрузка на SSD пригодится, если понадобится прогнать **генерацию
проекта** на 7B при нехватке памяти: тогда запускать `llama-server` по
команде из §2 и подключать его как отдельный провайдер.
