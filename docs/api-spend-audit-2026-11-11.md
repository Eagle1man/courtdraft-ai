## Почему локальный учёт мог занижаться

Даже без чужого дашборда есть четыре подтверждённых механизма:

1. **Неудачные и повторные HTTP-запросы не попадали в локальный отчёт.**
   В прогонах были десятки `All connection attempts failed` и пустых
   ответов; `TrackingProvider` записывал только успешный `_one_call`.

2. **Локальная цена считается по `prompt_tokens + completion_tokens`.**
   Если провайдер отдельно тарифицирует reasoning/cache-токены или
   считает по другой редакции цены, локальная сумма занижается.

3. **Часть вызовов ушла на другую модель.** 4 вызова выбрали
   `deepseek/deepseek-v4-flash-0731` (вход 8,39 / выход 27,06 ₽ за 1M)
   вместо дешёвой `deepseek-v4.1-flash-1017` (1,16 / 29,00).

4. **Слишком много прогонов с длинным контекстом.**
   50 + 30 + 10 + 3×3 + 35 block + 3×15 A/B — это больше 180 проектов
   и сотни вызовов. GraphRAG/pipeline добавили контекст: 49,6k → 63k
   токенов на 15 дел, при этом заметного выигрыша в A/B не было.

- Вести **append-only журнал каждого HTTP-вызова**, включая ошибки:
  `artifacts/budget_ledger.jsonl` (уже добавлен в `TrackingProvider`).

  токенам.
- Зафиксировать модель: `OPENAI_MODEL_AUTO=false` и явный
  `deepseek/deepseek-v4.1-flash-1017` на время замеров.
- Разделить ключи: приложение/eval и другие инструменты — разные ключи
  с разными лимитами.
- Не гонять 50 дел на каждый вариант. Для A/B — 10–15 дел, остальное
  локально/mock.
- GraphRAG и pipeline держать выключенными до подтверждённого A/B:
  `GRAPHRAG_ENABLED=false`, `MULTI_AGENT_ENABLED=false`.
