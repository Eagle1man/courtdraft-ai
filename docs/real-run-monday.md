# REAL-прогон: что сделать в понедельник

Дата подготовки: 2026-10-31. Всё, что можно было проверить без реальной
модели, проверено и записано ниже. На машине с RTX остаётся включить
режим и запустить одну команду.

На **этом** компьютере (CPU, 7,8 ГБ ОЗУ, видеокарты нет) 7B тоже
запускается — через подкачку и медленно: 2026-10-28 на нём считали 16
диагностических генераций (медиана 43,9 с), сегодня модель загрузилась и
ответила на пробный запрос за 33,2 с при 2,6 ГБ свободной памяти. Так что
«памяти нет» — это про скорость и запас, а не про невозможность: preflight
в таком случае предупреждает, а не запрещает.

## 1. Что должно быть на машине

| Что | Проверка | Ожидаемо |
|---|---|---|
| Драйвер NVIDIA | `nvidia-smi` | `Driver Version`, `CUDA Version` |
| Ollama | `ollama --version` | версия печатается |
| Сервер Ollama | `ollama serve` в отдельном окне | `http://127.0.0.1:11434` отвечает |
| Модель | `ollama list` | нужная модель в реестре |
| Память | свободно RAM + VRAM | модель с запасом 20% влезает в VRAM или RAM |

Модель 7B (файл ~4 ГБ) требует примерно 4,7 ГБ памяти с запасом на
контекст. Проверка различает два разных случая:

- **сейчас свободно меньше** — `WARN memory` с числом «сколько освободить»
  и подсказкой, кто занял (`scripts\memory_report.py`); запуск не
  запрещается, но без освобождения прогон уйдёт в подкачку;
- **модель больше всей памяти машины** — `FAIL memory`, генерация не
  запускается: здесь уже нужна другая машина или модель меньше.

Раньше проверка сравнивала модель с *текущей* свободной памятью и
объявляла невозможным прогон, который на этой же машине уже состоялся
(7B на 2026-10-28). Это была ошибка проверки, а не машины.

У RTX 3050 две версии — 4 и 6 ГБ. Модель `vikhr-7b` (файл 4,0 ГБ,
с запасом 4,7 ГБ) на 4-гигабайтной карте не поместится и пойдёт на CPU,
на 6-гигабайтной — поместится в VRAM при свободных 4,7 ГБ.

## 2. Переключить режим (только `.env`, код не меняется)

```ini
APP_ENV=runtime
LLM_PROVIDER=ollama
EMBEDDING_PROVIDER=local
OLLAMA_ENABLED=true
OLLAMA_BASE_URL=http://127.0.0.1:11434
OLLAMA_MODEL=vikhr-7b:latest
```

## 3. Проверить готовность

```powershell
cd D:\courtdraft-ai\backend
.venv\Scripts\python.exe -m app.llm.preflight
.venv\Scripts\python.exe -m app.llm.preflight --probe
```

`--probe` делает один короткий запрос к модели: это единственная
проверка, которая доказывает, что модель **отвечает текстом**, а не
пустым `content` (у Qwen3 ответ уходит в поле размышления).

Коды: `0` — готово, `2` — не готово (причина и подсказка в выводе).

## 4. Прогон

```powershell
cd D:\courtdraft-ai
backend\.venv\Scripts\python.exe scripts\real_run.py
```

Что произойдёт:

1. preflight с пробой;
2. копия демо-БД → `data/demo/output/real-run.db` (демо-стенд и рабочая
   БД не затрагиваются);
3. генерация проекта на реальной модели по делу `DEMO-001`
   (или `--case "<номер>"`);
4. отчёт `docs/real-run.json`: время, разделы (символы, мс, ошибки),
   статус проверки, замечания;
5. итог: `0` — прогон состоялся, `2` — не готово, `3` — генерация упала
   или раздел пуст.

Полезные ключи: `--no-probe` (не тратить время на пробу),
`--fresh` (пересоздать копию БД), `--case "2-105/2025"`.

## 5. На что смотреть в отчёте

- `sections[*].chars` — 0 символов значит «раздел не сформирован»;
- `sections[*].error` — техническая причина отказа;
- `sections[*].is_mock` — `true` в REAL-прогоне быть не должно
  (значит, провайдер не переключился);
- `sections[*].latency_ms` — фактическое время по разделам;
- `verification.status` и `issues` — сколько замечаний нашла проверка.

## 6. Что уже проверено сегодня (без модели и с моделью)

```powershell
backend\.venv\Scripts\python.exe scripts\real_run.py --no-probe
# → preflight: provider OK, ollama OK, model OK,
#   memory WARN (модель 4.0 ГБ влезает в 7.8, но свободно 2.1 —
#   «нужно освободить около 2.1 ГБ»; подсказка → memory_report.py)
#   embeddings WARN, генерация не запускается до освобождения памяти
```

`--self-test` проверяет то, что не зависит от модели: preflight,
копирование БД, генерацию, проверку, запись отчёта. Именно поэтому в
понедельник останется только модель, а не «сначала найдём ошибку в
обвязке».

### REAL-прогоны на этой машине (2026-10-31)

Здесь нет видеокарты, 7,8 ГБ ОЗУ. Обе модели влезают в память машины,
но идут по CPU с подкачкой. Оба прогона — на `DEMO-001`, `--fresh`.

**`qwen2.5:1.5b` (0,9 ГБ):**

```powershell
$env:OLLAMA_MODEL = "qwen2.5:1.5b"
backend\.venv\Scripts\python.exe scripts\real_run.py --fresh --no-probe
```

```
153.9 с; descriptive 977 симв. / 65.7 с, established 672 / 57.6 с,
motivating 0 / 30.3 с («текст оборван по лимиту ответа»);
проверка REVIEW_REQUIRED, 10 замечаний, CRITICAL 0; код 3
```

**`vikhr-7b:latest` (4,0 ГБ, `OLLAMA_NUM_CTX=2048`):**

```
490.2 с; descriptive 0 / 145.5 с, established 0 / 193.1 с
         («получен текст на неожиданном языке»),
         motivating 112 симв. / 150.0 с;
проверка REVIEW_REQUIRED, 10 замечаний, CRITICAL 1; 2 раздела пустые
```

Что это значит:

1. **REAL-путь работает на этой машине** с обеими моделями: Ollama,
   генерация, проверка, отчёт — без правок кода.
2. **7B здесь запускается, но не годится для проекта**: два раздела из
   четырёх модельных ушли в неверный язык, время — 8 минут на проект.
   Это не сбой проверки: правило «текст не на русском → раздел
   несформирован» сработало и пометило разделы.
3. **1,5B быстрее, но тоже неполный** (мотивировочная пустая).
4. Оба прогона вернули код 3: пустые разделы не проходят молча.
5. Для сравнения на RTX 3050 6 ГБ: там модель идёт на GPU и контекст
   держится в VRAM — эти цифры здесь получить нельзя, но baseline,
   с которым сравнивать, теперь есть.

### Сколько памяти и какая модель влезет

```powershell
backend\.venv\Scripts\python.exe scripts\memory_report.py
```

Печатает свободную RAM/VRAM, топ процессов по памяти и список моделей
Ollama в трёх состояниях: «влезет» (помещается в свободную память
сейчас), «освободить» (помещается в объём машины, но не в свободную
часть) и «НЕ влезет» (больше всей памяти — только другая машина или
модель меньше). Запас тот же 20%, что и в preflight, иначе инструменты
давали бы разные ответы. Модели эмбеддингов помечаются отдельно: их не
предлагают «для прогона проекта».

## 7. Чего не делать

- Не запускать `real_run.py` на `data/demo/output/demo.db` или рабочей
  БД: прогон добавляет версию проекта.
- Не считать `--self-test` доказательством качества модели: это
  заглушка, и в отчёте это помечено.
- Не выключать preflight «чтобы пошло»: если модель не влезает в
  память, падение будет посреди генерации, а не на проверке.
- Не публиковать тексты дел: в `docs/real-run.json` их нет, и добавлять
  не нужно.
