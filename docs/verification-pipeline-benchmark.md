# Benchmark проверок — baseline (Этап 1)

Дата: 2026-10-31. Воспроизводимость: `scripts/verification_benchmark.py`.
Сырые числа: `docs/verification-benchmark-baseline.json`.

## Что и как измеряется

Скрипт прогоняет три блока и печатает результат. Никакая модель не
вызывается: измеряются **детерминированные правила**.

### 1. Резолютивная часть

Источник: `backend/tests/data/resol_fixtures.json` — размеченный датасет.
У каждой фикстуры есть вид (`defect`, `clean`, `disputed`), ожидаемые
идентификаторы срабатываний и список допустимых.

```
проверок в реестре: 25
фикстур defect+clean: 45 (clean: 14)
ожидаемых срабатываний: 31, найдено: 31 (100%)
ложных срабатываний на clean: 0
```

### 2. Денежные суммы

`app/drafting/numeric_guard.py` на 4 случаях: выдуманная сумма,
подтверждённая, итог из слагаемых, разный формат записи.

```
верно: 4/4
```

### 3. Подсудность

`app/verification/jurisdiction.py` на 5 случаях: 89 122 руб. у мирового
судьи, 40 000 у мирового, 150 000 в районном, 40 000 в районном,
потребительский спор 89 122 у мирового.

```
верно: 5/5
```

## Ограничение, без которого цифры читаются неверно

Датасет **синтетический**, и тест `test_every_check_has_defect_fixture`
требует, чтобы для каждой проверки была defect-фикстура. Поэтому 100 %
означают покрытие правил, а не качество на реальных судебных актах.
Независимой выборки реальных обезличенных дел в проекте нет.

Отдельно: 14 `clean`-фикстур показывают отсутствие ложных срабатываний
только на этих 14 текстах. Этого недостаточно для утверждения о низком
false positive rate на практике.

## Что не покрыто детекторами

| Класс ошибки | Есть ли проверка |
|---|---|
| Сумма существует, но относится к другому требованию | нет |
| Противоречащие даты в разных документах | нет |
| Пропущенное существенное требование | частично (`INCOMPLETE`) |
| Рассогласование мотивировочной и резолютивной | частично |
| Инструкция внутри документа (prompt injection) | нет |
